Security Policy

This Security Policy outlines the intended security practices for the Borongan City Transport Terminal QR-Based Transport Ticketing and Fee Collection System.

Policy Document Drivers · Cashiers · Staff · Administrators

This Security Policy describes how the system is designed to protect user accounts, driver information, QR identification, prepaid balance records, terminal transactions, administrative functions, and other system resources from unauthorized access or misuse. It covers account security, role-based access, login protection, data protection, transaction security, database security, audit logging, session security, password handling, and incident reporting.

—

Policy Overview

The policy describes how the system is designed to protect user accounts, driver information, QR identification, prepaid balance records, terminal transactions, administrative functions, and other system resources from unauthorized access or misuse.

01

Account Security

All users are responsible for protecting their assigned system accounts.

Users should:

  • Keep usernames and passwords confidential.
  • Never share account credentials with another person.
  • Use only their assigned account.
  • Log out after using the system.
  • Avoid saving passwords on shared or public computers.
  • Report suspected unauthorized account access.
  • Use strong passwords where supported by the system.

Users should not attempt to access another person's account.

02

Role-Based Access Control

The system uses role-based access to separate the functions available to each type of user.

Driver

Access to the driver's own profile information, Driver ID, QR code, vehicle information, prepaid balance, and transaction history.

Cashier

Access to functions required for driver identification, prepaid balance loading, payment/reference recording, and cashier transaction records.

Staff

Access to functions required for QR scanning, driver verification, transaction validation, terminal transaction processing, and transaction records.

Administrator

Access to broader system-management functions: user management, driver record management, fee configuration, transaction monitoring, reports, audit records, and administrative settings.

Users should not attempt to access features outside their assigned role.

03

Login Security

The login system should verify that the user has valid credentials before granting access to the system.

After successful authentication, the system should direct the user to the appropriate dashboard based on the account's assigned role.

For example:

Driver Login → Driver Dashboard
Cashier Login → Cashier Dashboard
Staff Login → Staff Dashboard
Admin Login → Admin Dashboard

Users should not be able to access another role's dashboard simply by changing a page address or manually navigating to a restricted page.

04

Driver Information Protection

Driver information may include personal, vehicle, license, account, and transaction-related information. Access to this information should be restricted according to the user's assigned role.

The system should prevent unauthorized users from viewing or modifying restricted driver records. Administrative access should only be provided to authorized personnel.

05

QR Code Security

The QR code is intended primarily for driver identification and terminal verification. The QR code should not expose unnecessary personal information.

When scanned, the system should retrieve only the information required for the authorized terminal process. Detailed driver information should remain protected by role-based access controls.

A QR code should not automatically provide unrestricted access to the driver's account.

06

Hardware Scanner Security

The designated QR scanner should only be used by authorized terminal personnel.

Staff should:

  • Use the designated scanner for authorized transactions.
  • Avoid connecting unknown devices to the terminal workstation.
  • Report scanner problems or suspicious behavior.
  • Ensure the correct driver record appears after scanning.
  • Confirm the transaction before completing it.

A successful scan does not automatically mean that a transaction should be completed. Driver status and transaction requirements must still be checked.

07

Prepaid Balance Security

Prepaid balance information is an important part of the system. The system should protect:

  • Current balance
  • Load amounts
  • Deducted amounts
  • Payment/reference information
  • Loading history
  • Transaction history

Only authorized Cashier and Administrator accounts should have access to functions that modify prepaid balance records according to their assigned responsibilities.

Staff should not be given unnecessary access to modify prepaid loading records. Drivers should only be able to view their own balance and related information.

08

Transaction Security

Terminal transactions should be processed only through authorized system functions.

Before a transaction is completed, the system should verify applicable information such as:

  • Driver identity
  • Driver account status
  • Registered vehicle
  • Applicable fee
  • Available prepaid balance
  • Transaction status

Once successfully processed, the transaction should be recorded in the centralized transaction database.

The system should prevent duplicate or incomplete transactions where the implemented system controls support such prevention.

09

Database Security

System records should be protected from unauthorized access, modification, deletion, or disclosure.

The database may contain:

  • Driver records
  • Vehicle records
  • User accounts
  • Prepaid balances
  • Payment/reference records
  • Transaction records
  • Reports
  • Audit information

Database access should be limited to authorized system functions and authorized personnel. Where a hosted database service is used, appropriate access controls should be applied. Database credentials and private configuration information should never be exposed in publicly accessible source code.

10

Administrative Security

Administrator accounts have broader access and therefore require additional protection.

Administrators should:

  • Use only their assigned administrator account.
  • Protect administrator credentials.
  • Avoid sharing administrator access.
  • Review important system changes.
  • Correct inaccurate records only when authorized.
  • Monitor unusual account or transaction activity.
  • Avoid unnecessary modification of database records.

Administrative privileges should only be provided to authorized personnel.

11

Driver Information Modification

Administrators may be permitted to correct inaccurate driver information according to the system's administrative procedures.

Changes may include:

  • Driver name
  • Address
  • Contact information
  • Vehicle type
  • Plate number
  • License information
  • Account status

When audit logging is implemented, important changes should record:

  • Who made the change
  • What record was changed
  • When the change occurred
  • What information was modified

Updated information should automatically reflect in system areas using the same authorized database record.

12

Audit Logs and Accountability

Important system activities should be recorded through an audit log where this functionality is implemented.

Audit records may include:

  • User account
  • User role
  • Activity performed
  • Date and time
  • Affected record
  • Previous value, where applicable
  • Updated value, where applicable

Activities that may require auditing include:

  • Driver information changes
  • User account management
  • Account status changes
  • Fee configuration changes
  • Payment/reference updates
  • Transaction-related administrative actions

Audit logs help determine:

Who performed an action
What happened
When it happened
Which record was affected
13

Session Security

Users should properly end their system session after completing their work. This is especially important when using shared terminal computers.

The system should provide appropriate session controls where supported, such as:

  • Logout
  • Session expiration
  • Restricted access after logout
  • Re-authentication for protected functions

Users should not leave an authenticated account unattended on a shared workstation.

14

Password Security

Passwords should be handled securely by the system.

Passwords should not be:

  • Displayed publicly
  • Shared between users
  • Stored in plain text where secure password storage is available
  • Included in publicly accessible source code
  • Written in publicly accessible project documentation

Users should change compromised credentials according to the available account-management procedures.

15

Source Code and Configuration Security

Project source code and configuration files may contain information required to connect the website to system services. Sensitive configuration information should not be publicly exposed.

Examples include:

  • Database credentials
  • API keys
  • Authentication secrets
  • Service-role keys
  • Private configuration values

Public repositories should contain only information that is safe to expose.

16

Backup and Recovery

Important system records should be protected against accidental loss where backup functionality is available.

Backup procedures may include:

  • Database backups
  • Recovery procedures
  • Preservation of important transaction records
  • Protection of backup files

Backup access should be restricted to authorized personnel. The actual backup schedule should only be stated if it has been implemented or formally established.

17

Security of Reports

Reports may contain personal and transaction-related information. Generated reports should therefore be handled carefully.

Authorized personnel should:

  • Access only reports relevant to their responsibilities.
  • Avoid unnecessarily sharing reports.
  • Protect printed reports from unauthorized access.
  • Store digital reports securely.
  • Dispose of sensitive printed records appropriately according to applicable procedures.
18

Security Incident Reporting

Users should report suspected security problems as soon as possible.

Examples include:

  • Unauthorized account access
  • Unknown login activity
  • Missing or altered driver information
  • Suspicious transaction activity
  • Unexpected balance changes
  • Lost or compromised credentials
  • QR codes that appear to be misused
  • Unauthorized access to restricted pages
  • Suspicious system behavior

Reports should be provided to the responsible terminal office, administrator, adviser, or designated project personnel according to the applicable procedure.

19

Security Response

When a security concern is reported, authorized personnel should review the incident and take appropriate action.

Possible actions may include:

  • Reviewing account activity
  • Checking transaction records
  • Reviewing audit logs
  • Temporarily restricting an affected account
  • Correcting unauthorized records
  • Resetting compromised credentials
  • Investigating system configuration
  • Documenting the incident

The response should depend on the nature and seriousness of the security concern.

20

User Responsibilities

All system users are expected to help maintain system security.

Users should:

  • Use their assigned accounts.
  • Keep credentials confidential.
  • Verify information before completing transactions.
  • Protect Driver IDs and QR codes.
  • Avoid unauthorized system access.
  • Report suspicious activity.
  • Log out after using shared workstations.
  • Follow applicable terminal procedures.
21

Security Review and Updates

The security practices of the system should be reviewed when:

  • New system features are added
  • User roles change
  • Database structures are modified
  • New third-party services are introduced
  • Authentication procedures change
  • Security concerns are identified
  • Institutional requirements change

Security controls should be improved as the system develops.

—

Important Security Boundary

Policy Scope

This Security Policy describes the intended security practices of the academic project.

It does not claim that the system has a particular government security certification, cybersecurity certification, or formal compliance status unless such certification or compliance has actually been established by the responsible authority.

The project should not claim to provide security controls that have not been implemented or formally approved.

Actual security procedures for the Borongan City Transport Terminal should follow the requirements established by the responsible office and applicable institutional and legal requirements.

—

Security Reminder

The security of the system depends on both technical controls and responsible user behavior.

A secure workflow can be summarized as:

Authenticate
Verify Role
Access Authorized Information
Process Authorized Action
Record Activity
Monitor
Report Concerns
